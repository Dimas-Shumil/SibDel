## Диагностика предупреждения pg

Пользователь запустил оба smoke с --trace-deprecation на отдельной тестовой БД.
В обоих CLI-процессах получен одинаковый путь:

```text
Client.query (pg/lib/client.js:762)
PgTransaction.performIO (@prisma/adapter-pg/dist/index.mjs:645)
PgTransaction.queryRaw (@prisma/adapter-pg/dist/index.mjs:595)
@prisma/client/runtime/client.js → interpretNode
```

Подтверждено:

1. Предупреждение возникает в CLI smoke, а не только потенциально в сервере.
   Вывод сервера с trace не предоставлен; отсутствие warning в сервере не заявляется.
2. В pg 8.23.0 условие warning — `_queryQueue.length > 0 && !pipeline`.
   Это сигнал о постановке запроса в занятую очередь одного Client.
3. В adapter-pg 7.10.0 PgTransaction работает с одним соединением из pool;
   performIO напрямую вызывает await this.client.query(config), без собственной
   очереди/мьютекса. Параметры передаются одним объектом: гипотеза о двойном
   аргументе values для этой установленной версии не подтверждается.
4. В Inventory smoke Promise.all запускает самостоятельные вызовы
   updateOrderStatus/receiveInventory, каждый через runSerializable(prisma,...).
   В Subscriptions smoke одновременно запускаются две самостоятельные генерации.
   Они нужны для проверки идемпотентности; сами по себе не доказывают совместное
   использование одного transaction client приложением.
5. В updateOrderStatus есть чтения внутри transaction с несколькими relations
   (user, items, inventoryReservations); loadGenerationSubscription также читает
   user, address, items/product в одном transaction. В проверенных этих путях
   нет явного Promise.all над одним transaction client.
6. Отдельно найден Promise.all над transaction.productImage в загрузке фото
   (admin-catalog.service.js). Эти smoke загрузку фото не вызывают, поэтому
   приписывать ему предоставленный warning нельзя. Этот участок не менялся.

Наиболее вероятный механизм — внутренние параллельные relation-запросы Prisma
на одном transaction connection. Это вывод по совокупности исходников, стека
пользователя и аналогичного upstream issue, а не собственное воспроизведение
на PostgreSQL и не доказательство точной пары SQL-запросов.

Первичные источники, просмотренные 15.10.2026:

- https://github.com/prisma/orm/issues/29407 — аналогичный стек и сообщения о
  multiple includes, включая чтение внутри явной транзакции. Наличие связанных
  коммитов в issue не доказывает выпуск исправления в установленной версии.
- https://github.com/brianc/node-postgres/issues/3612 — объяснение владельца pg:
  не отправлять следующий запрос на занятое соединение; warning один раз за runtime.
- https://github.com/prisma/orm/issues/29646 — другой отчёт; его гипотеза о values
  не соответствует просмотренному коду установленного adapter-pg 7.10.0.

Решение в этом патче: не менять рабочие сервисы ради неподтверждённого обхода.
Не понижать pg ради исчезновения warning, не включать NODE_NO_WARNINGS,
не убирать конкурентные проверки, не повышать pg до 9 без проверки совместимости.
Дальнейшее исправление требует либо подтверждённого upstream-релиза с проверкой
на тестовой БД, либо отдельного диагностического воспроизведения с фиксацией
пересекающихся запросов без значений параметров/персональных данных.

## Конфликты Serializable — отдельный результат

Inventory вывел P2010 / SQLSTATE 40001, затем PASS: резерв 1 единицы снят,
физический остаток остался 24; два конкурентных поступления добавили ровно 3
и создали ровно 2 движения.

Subscriptions вывел конфликт записи при order.create, затем PASS:
subscription #7, order SD-261015-CF90B80A57; проверены pricing, Promotions,
владелец адреса, резерв, due-date guard, скрытые товары, pause/resume,
идемпотентность. Это результаты пользователя от 15.10.2026.

Такой итог согласуется с ожидаемым конфликтом и успешным retry, а не с провалом
smoke. Он не доказывает безопасность любого другого конфликта/сценария.
runSerializable не менялся: максимум 3 попытки; P2034 либо P2010 с точным 40001
в meta.code или meta.driverAdapterError.cause.originalCode. Текст ошибки для retry
не используется. SMTP, остатки, аудит и checkout owner binding не менялись.

Ничего не удалять, npm install и миграции для этого патча не нужны.
После диагностики остановить тестовый сервер через Ctrl+C.
В каждом CMD, где выбиралось тестовое окружение, отдельно выполнить:

```bat

```

Для обычного сервера после очистки переменных: npm start (ожидается 3001).
Очистка DOTENV_CONFIG_PATH не снимает другие переменные process.env: при
неожиданном окружении проверить их локально, не публикуя секреты.

## Открыто перед публикацией

- Warning pg не устранён; точный SQL overlap и поведение серверного процесса
  пока не зафиксированы. Совместимость с pg 9 не подтверждена.
- Полный npm audit: 3 High в dev-цепочке; production audit: 0 на дату проверки.
- Не предоставлены реальный домен, VPS/IP, ОС, пользователь и пути.
  Deploy-файлы этапа 6 остаются шаблонами; PM2/Nginx/TLS/reboot/timers
  на целевом сервере не проверены.
- Настоящий PostgreSQL backup/restore и восстановление uploads не выполнены.
  Dump и live uploads не атомарно согласованы; нужно окно остановки записей
  либо проверенная snapshot-процедура. RPO/RTO не измерены.
- Offsite backup и внешний канал оповещения не настроены.
- Доставка настоящего уведомления нового заказа не подтверждена.
- Реквизиты, контакты, график, реальные пункты выдачи и юридические условия
  требуют подтверждения. Документы этапа 4 — проекты/noindex.
- «Самовывоз — Абакан», ул. Тестовая, д. 1 — тестовые данные, не реальный адрес.
- SEO_SITE_URL требует реального домена; seo-check.example не production origin.
- Ценовая фильтрация/сортировка каталога загружает набор кандидатов;
  масштабирование требует отдельной проверки. Полное соответствие WCAG не заявлено.

Итог: локальная функциональная приёмка подтверждена в указанном объёме;
эксплуатационная приёмка и публикация остаются отдельным незавершённым этапом.
