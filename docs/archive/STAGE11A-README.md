# SibDel · этап 11A — PWA и клиентские сессии

Дата подготовки: 28 октября 2026. Исходник: приложенный архив `sibDel — копия(20261028-073648).zip`.

Это первый независимый патч из разрешённого в задании разделения. В нём реализованы PWA и долговременная авторизация покупателей. PUSH, массовые рассылки и центр уведомлений остаются отдельными следующими этапами; этот архив не выдаёт их за готовые. Production не изменялся.

Из существующей мобильной навигации есть шапка, поиск, кнопки аккаунта/корзины и раскрывающееся меню с каталогом/акциями. В 11A оставляем её: изменение сессий и установка не требуют перестройки навигации. Нижняя панель PWA и её safe-area/клавиатура будут оцениваться вместе с центром уведомлений на этапе 11C.

## Как работает 11A

- `/manifest.webmanifest`: стабильный id `/`, start_url `/`, scope `/`, standalone, PNG 192/512 и maskable 512, Apple icon 180; установка доступна без аккаунта.
- Иконки построены из существующего знака-ели и цветов сайта. Исходник находится в `public/pwa/icon.svg`.
- `/sw.js`: отдельная выдача Express с `Cache-Control: no-store`, JavaScript MIME и `Service-Worker-Allowed: /`.
- Единственный CacheStorage — `sibdel-pwa-11a-1`. В нём шесть публичных ресурсов: offline.html, pwa.min.css и четыре PNG. Никакого runtime-кеша страниц/товаров/API/скриптов приложения.
- Навигация идёт через сеть с `cache: no-store`; при сетевой ошибке возвращается общая offline-страница. HTTP 4xx/5xx не заменяются успешным offline-ответом. `/api`, `/admin`, `/uploads`, `/components`, POST и внешние запросы обходят SW.
- Нельзя исключить `/admin` из scope `/` средствами manifest: вместо этого SW вообще не перехватывает административные запросы. На административных страницах установочный JS не подключён.
- Обновление SW остаётся в waiting до закрытия всех вкладок и PWA. Показывается объяснение без принудительной перезагрузки и без skipWaiting: даже checkout в соседней вкладке сохраняет введённые данные. При будущих изменениях offline-ресурсов повышать VERSION в sw.js.
- Баннер появляется через 10 секунд от начала посещения, когда есть beforeinstallprompt либо определён Safari на iOS/iPadOS. «Позже», крестик и свайп вверх закрывают его. Повторных показов на внутренних переходах нет. Новое посещение — новая вкладка/новое sessionStorage либо возврат после 30 минут отсутствия активности. Показ в скрытой вкладке отложен до её открытия.
- Android вызывает сохранённый beforeinstallprompt только по нажатию. На Safari показывается инструкция «Поделиться» → «На экран Домой» → «Добавить». Встроенным браузерам и другим меню iOS автоматическая инструкция не навязывается; сайт можно открыть в Safari.
- Флаг установленного приложения хранится локально только для UI. Токен авторизации там не хранится. На Safari нет надёжного события установки из обычной вкладки: факт запуска standalone сохраняется в доступном ему хранилище; изолированная браузерная вкладка может не знать об установке. Системные ограничения не подменяются обещанием универсального определения установки.
- В PWA и после известной установки баннер скрыт. На checkout, страницах входа/регистрации/сброса пароля и в админке не запускается регистрация/установочный UI. Есть клавиатурные кнопки, Escape, touch-свайп и prefers-reduced-motion.

## Клиентские сессии и совместимость

`CUSTOMER_SESSION_TTL_DAYS` — новый необязательный параметр (по умолчанию 90, допустимо 1–90). `SESSION_TTL_DAYS` остаётся прежним параметром срока служебных сессий; значение в существующем `.env` патч не меняет.

Создание сессии читает действительную роль из БД. CUSTOMER получает 90 дней, OWNER/STAFF — существующий фиксированный срок (в примерах 30 дней). При активности покупателя продлеваются и expiresAt в БД, и HttpOnly/Secure/SameSite=Lax cookie. Запись активности/продление ограничены интервалом около 15 минут; возможное отклонение idle-границы — до 15 минут. Cookie переиздаётся до подтверждённой сервером даты, а не на произвольные 90 дней при каждом ответе.

Существующие неистёкшие клиентские сессии обновляются при первом обращении к API. Истёкшие или отозванные сессии не восстанавливаются: нужен вход. Политика не требует миграции, переименования cookies или массового выхода. Сервер каждый раз проверяет существование сессии и активность аккаунта. При конкурентном продлении проверяет результат updateMany: удалённая logout/сбросом сессия не создаётся заново. Запрос, уже прошедший авторизацию до отзыва, может завершиться — обычная граница существующего middleware; следующий запрос будет отклонён.

Продление не выполняется для OWNER/STAFF. Публичный middleware принимает только CUSTOMER, административный — OWNER/STAFF. Даже ручная подмена имени cookie не переносит клиентский вход в админку. Имеющиеся logout, список устройств, смена/сброс пароля и блокировка продолжают действовать. При смене пароля в кабинете все старые токены отзываются, а текущему устройству существующий controller выдаёт новую сессию; при восстановлении пароля нужен новый вход.

90 дней — серверный срок, а не гарантия вечного хранения браузером: очистка данных, приватный режим, переустановка приложения или политика ОС могут потребовать входа. Первичный вход в iOS PWA может потребоваться отдельно от Safari.

## Установка на Windows (PowerShell)

1. Сохранить ZIP отдельно от проекта и распаковать в новый каталог, например `C:\Temp\sibdel-stage11a`. Корень распакованного каталога должен содержать app.js и STAGE11A-FILES.json. Патч также можно распаковать поверх проекта после собственной резервной копии; проверяемый способ ниже надёжнее.
2. Остановить локальный Node/Go Live. PWA и API проверять через Express, а не через Go Live.
3. Проверить checkout; команды не исправляют и не сбрасывают Git:

```powershell
Set-Location 'C:\Projects\SibDel'
git remote -v
git branch --show-current
git rev-parse HEAD
git status --short
node --version
```

Нужен Node 24.x. Проверить, что это нужный репозиторий PabloAlligator/SibDel либо Dimas-Shumil/SibDel, ветка main, а текущие правки сохранены. Точный путь выбрать по своему компьютеру.

```powershell
$Patch = 'C:\Temp\sibdel-stage11a'
$Project = 'C:\Projects\SibDel'
$Backup = 'C:\Temp\sibdel-before-stage11a'
node "$Patch\scripts\stage11a-patch.mjs" check "$Project"
node "$Patch\scripts\stage11a-patch.mjs" apply "$Project" "$Backup"
node "$Patch\scripts\stage11a-patch.mjs" verify "$Project"
Set-Location $Project
npm ci
npm run test:unit
npm run test:pwa
npm run prisma:validate
npm run dev
```

`$Backup` должен быть новым, ещё не существующим каталогом вне проекта/патча. Установщик сначала проверяет хеши всех исходных/новых файлов, сохраняет заменяемые файлы и только затем копирует патч. Расхождение с архивом останавливает установку до записи: сравнить конкретные файлы и перенести изменения вручную, не отключать проверку вслепую. Точная проверка может обнаружить и различие CRLF/LF.

Новых runtime-зависимостей нет, package-lock.json не меняется. Собранные pwa.css/pwa.min.css уже включены; существующие CSS не заменяются. `npm run scss` умеет пересобрать PWA, но одновременно пересобирает все стили проекта: перед коммитом проверить его diff, поскольку в исходном архиве некоторые CSS отличались от SCSS.

Для обычного запуска использовать существующую локальную `.env`; патч её не содержит и не заменяет. Для проверки схемы нужна DATABASE_URL, но `prisma:validate` к базе не подключается. Миграции и seed для 11A не нужны.

Дополнительная браузерная проверка (временная dev-зависимость, не production):

```powershell
npm install --no-save --package-lock=false playwright
npx playwright install chromium
npm run test:pwa-browser
```

Сценарий запускает временный HTTP fixture на 127.0.0.1 со страницами проекта и CSP, не импортирует production server.js, не подключается к PostgreSQL/SMTP и не отправляет сообщения. Системный диалог установки проверяется вручную; в автоматике beforeinstallprompt имитируется. Safari здесь проверяется как вариант UI по user agent, а не движком WebKit.

Проверять HTTPS staging либо локальный localhost на компьютере. Обычный HTTP IP компьютера в Wi-Fi не является безопасным контекстом для SW.

- [ ] Android Chrome: открыть без входа; до 10 секунд баннера нет, после — есть при доступной установке; системное окно появляется только по кнопке.

## Безопасная выкладка на Ubuntu 24.04

Только после проверки и отдельного подтверждения владельца. Эти действия здесь не выполнялись. SSH-логин не указан намеренно — использовать свой настроенный доступ к 194.226.112.201. Не применять `reset --hard`, migrate reset, seed, не менять рабочую PostgreSQL, `.env`, uploads или действующий Nginx вслепую.

1. Передать ZIP на VPS в отдельный временный каталог, распаковать вне `/var/www/sibdel`.
2. Проверить код, каталог и процесс:

```bash
cd /var/www/sibdel
pwd
git remote -v
git branch --show-current
git rev-parse HEAD
git status --short
node --version
pm2 describe sibdel
```

3. Убедиться, что есть актуальная штатная резервная копия БД и файлов; проверить её существующим регламентом. Этот патч БД не изменяет. Сопоставить действующий Nginx с принципом проксирования всех public URL в Express. Для `/sw.js` не должно быть CDN/proxy/static-кеша. Файлы nginx.conf.example и systemd патч не заменяет.
4. Выполнить проверку до остановки процесса:

```bash
node /tmp/sibdel-stage11a/scripts/stage11a-patch.mjs check /var/www/sibdel
```

При несовпадении хешей остановиться и сверить изменения. Данный патч привязан к приложенному архиву, а не к неподтверждённому Git-коммиту.

5. В согласованное окно (короткая остановка сайта) применить патч от пользователя, которому принадлежат файлы/PM2. Каталог backup ниже должен быть новым и находиться вне проекта/патча. При необходимости предварительно создать `/var/backups/sibdel-code` и выдать доступ по своему регламенту.

```bash
pm2 stop sibdel
node /tmp/sibdel-stage11a/scripts/stage11a-patch.mjs apply /var/www/sibdel /var/backups/sibdel-code/stage11a-before
node /tmp/sibdel-stage11a/scripts/stage11a-patch.mjs verify /var/www/sibdel
cd /var/www/sibdel
npm run test:unit
pm2 restart sibdel
```

Зависимости и lock не меняются, поэтому на VPS с уже рабочим node_modules переустановка не требуется. В новой staging-копии выполнить `npm ci`. Если production установлен с `--omit=dev`, для проверки unit/runtime хватит существующих runtime dependencies; Sass/Prisma CLI понадобятся только для сборки/validate в отдельной среде. Не выполнять Prisma migrate deploy ради 11A: новой миграции нет, а команда может неожиданно применить старые неприменённые миграции.

Новая переменная optional, без неё действует 90 дней. Если хотите задать её явно, вручную добавить `CUSTOMER_SESSION_TTL_DAYS=90` в действующий `.env`, сохранив остальные значения и прежний SESSION_TTL_DAYS. После изменения окружения использовать принятый в проекте способ перезапуска PM2 с актуальным env; не копировать production.env.example поверх `.env`.

## Откат

Простое удаление sw.js не удаляет уже установленный worker. Для отката нужен сохранённый retirement worker по тому же URL `/sw.js`.

1. Остановить процесс. Откатить код из backup: установщик откажется перезаписывать файлы, которые изменились после патча; при частичном применении пропускает уже исходные файлы и восстанавливает остальные.

```bash
pm2 stop sibdel
node /tmp/sibdel-stage11a/scripts/stage11a-patch.mjs rollback /var/backups/sibdel-code/stage11a-before
```

2. После rollback исходный Express умеет раздавать `public/sw.js` через static. Скопировать retirement worker из сохранённого распакованного патча, оставив URL доступным и некешируемым:

```bash
cp /tmp/sibdel-stage11a/deploy/pwa-retire.js /var/www/sibdel/public/sw.js
pm2 restart sibdel
curl -fsSI https://sib-del.ru/sw.js
curl -fsS https://sib-del.ru/api/health
```

Старый static Express по умолчанию даёт max-age=0 (ревалидация). Если Nginx/CDN добавляет длительный кеш, сначала исправить это точечно по проверенной конфигурации; sw.js должен приходить новым при update. Retirement worker активируется через skipWaiting, удаляет только кеши `sibdel-pwa-*`, отменяет регистрацию и не перезагружает открытые страницы. Это специальное поведение отката, не штатного обновления. Сохранять retirement URL доступным длительно: вернувшиеся через недели устройства тоже должны получить его. На тестовом устройстве дополнительно закрыть окна/PWA и открыть снова либо выполнить ручной update worker в DevTools.

Миграций нет, восстанавливать/заменять PostgreSQL не нужно. Продлённые expiresAt остаются в существующих строках UserSession; старый код понимает их, но больше не продлевает. Для немедленного завершения отдельных входов использовать штатное управление сессиями/блокировку, не массовую очистку БД.

На Windows такой же откат выполняется `node "$Patch\scripts\stage11a-patch.mjs" rollback "$Backup"`; затем скопировать `$Patch\deploy\pwa-retire.js` в `$Project\public\sw.js` и перезапустить локальный Express.

## Следующие независимые патчи

11B: Web Push/VAPID, таблицы подписок устройств/согласий/transactional outbox/рассылок, дедупликация в транзакциях заказов и SubscriptionEvent, OWNER-only API/админка, тест на своё устройство, планировщик systemd, лимиты/отмена/retry и удаление 404/410 подписок. До реализации необходимо проверить актуальные российские требования к рекламным сообщениям и форме/доказательству согласия. Браузерное разрешение само по себе маркетинговым согласием не считается. VAPID-секреты и новый таймер сейчас не нужны.

11C: центр уведомлений, read/unread, изоляция покупателей, категории/отзыв маркетинга, история независимо от доставки PUSH, deep links и оценка нижней навигации для standalone с safe-area и клавиатурой. Открытия считать только по реально зарегистрированным кликам; «доставлено пользователю» не выводить из ответа push-сервиса.

Первый этап не запрашивает Notification permission, не создаёт браузерные PUSH-подписки, ничего не рассылает и не добавляет фиктивные пункты управления PUSH.
