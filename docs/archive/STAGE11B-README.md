# SibDel · 11B — Web Push и OWNER-рассылки

28 октября 2026. Патч поверх проверенного этапа 11A / коммита `103dc89`, отправленного в `Dimas-Shumil/SibDel`. Production не изменялся. Все примеры ниже — инструкции для последующей установки, а не выполненные на VPS действия.

## Что готово

- Web Push: VAPID, привязка устройства к пользователю и серверной сессии, включение по кнопке и отключение устройства. Разрешение браузера не запрашивается при загрузке страницы.
- Настройки покупателя в `/account/settings`: заказы, изменения подписки, отдельное добровольное рекламное согласие и его отзыв. Устройства других пользователей не раскрываются и не могут быть переназначены чужому аккаунту.
- Сервисные уведомления о NEW/CONFIRMED/ASSEMBLING/READY/DELIVERING/COMPLETED/CANCELLED заказах. READY для самовывоза получает соответствующий текст. Для гостей уведомления в чужой кабинет не создаются.
- Изменения подписки и ошибка формирования регулярного заказа. Повтор одинакового изменения не создаёт повторное уведомление; возвращение к прежним настройкам после другого состояния считается новым изменением.
- Durable outbox: запись уведомления создаётся SQL-триггером в той же транзакции, что заказ/изменение статуса/событие подписки. При rollback нет уведомления. Повтор checkout или неизменившийся статус не создаёт второй записи. Внешняя отправка не выполняется внутри бизнес-транзакций.
- `/admin/push`: доступ только OWNER, включая HTML, API, encoded/case aliases. Черновики, заголовок/текст/внутренняя ссылка, необязательное изображение из уже загруженных товаров/картинок сайта; тест на своё устройство; отправка сейчас/по расписанию; группы всех согласившихся покупателей либо покупателей с активной регулярной подпиской; история с пагинацией, состояниями, ошибками и измеряемыми кликами; отмена ещё не запущенной рассылки.
- Серверный обработчик `npm run push:process` и шаблоны systemd service/timer. Пример запуска — каждую минуту, без одновременных экземпляров одного systemd service. При backlog/долгой обработке фактическая отправка может быть позже запланированной даты.
- Данные уведомления сохраняются, даже если устройство не подключено или push не доставлен. Полный клиентский центр истории/read-unread/нижняя PWA-навигация остаётся отдельным этапом 11C. Этот патч не добавляет фиктивный интерфейс истории.

## Изменения архитектуры

Существующие checkout, склад, расчёт цен, платежи, корзина, SMTP и бизнес-переходы статусов не переписаны. Новые модули: push policy/config, сервис настроек/кампаний, outbox worker, HTTPS transport, маршруты, JS настройки покупателя/владельца и обработчики SW.

Новые таблицы:

| Таблица | Назначение |
| --- | --- |
| PushPreference | Категории, состояние/версия рекламного согласия, суточный лимит |
| PushConsent | Неизменяемая история grant/revoke: аккаунт, ID сессии, текст, версия, время |
| PushDevice | Endpoint/ключи, владелец, серверная сессия, состояние устройства |
| PushCampaign | Черновик, аудит создателя, сегмент, расписание, курсор обработки |
| CustomerNotification | Сохранённое событие, deep link, будущая история; реальные click/read timestamps |
| PushJob | Уникальная пара уведомление/устройство и состояние попытки |
| PushSubscriptionState | Последнее значимое состояние подписки и его ревизия для дедупликации |

Единственная новая миграция: `prisma/migrations/20261028110000_web_push/migration.sql`. Она добавляет новые таблицы/индексы/FK/функции/триггеры. Существующие записи не удаляются, не заменяются и не отправляются задним числом. Миграция выполняется в BEGIN/COMMIT, с lock_timeout 5 секунд и statement_timeout 60 секунд. При занятой таблице она может завершиться ошибкой вместо долгого блокирования магазина; не применять её повторно вслепую при ошибке Prisma.

Привязка PushDevice к UserSession использует cascade: logout, смена пароля, отзыв входа или блокировка убирают соответствующие устройства. PushJob сохраняется с deviceId=NULL, чтобы статистика не исчезала при удалении устройства. 404/410 push-провайдера отключают устройство. Оно остаётся в списке с отметкой: пользователь может удалить подключение, затем подключить его заново. Явное отключение удаляет endpoint/ключи, сохраняя задачи с deviceId=NULL. Старые endpoints не выдаются в API и не печатаются в журнале.

Generated Prisma TS-клиент включён в патч и соответствует Prisma 7.10.0. Schema и generated файлы должны обновляться вместе; `prisma:generate` после установки остаётся проверкой воспроизводимости. В архиве нет node_modules, .git, .env, SQL-дампов, пользовательских uploads или VAPID-секретов.

## Семантика доставки и ограничения

- Очередь и пары notification/device уникальны. PENDING атомарно переходит в SENDING до обращения к провайдеру; конкурентный worker не захватывает ту же задачу повторно.
- При успешном HTTP-ответе провайдера состояние ACCEPTED означает только «принято push-сервисом». Доставка на телефон и прочтение из него не выводятся.
- При 4xx — FAILED; 404/410 дополнительно отключают устройство. 5xx, разрыв сети/таймаут и прерванная отправка — UNKNOWN. Старый SENDING через 10 минут становится UNKNOWN. Автоматической повторной отправки нет: нельзя безопасно отличить потерянный ответ от уже принятого сообщения. Уведомление при этом остаётся в БД.
- SW хранит только ID и время получения в IndexedDB до 30 дней и подавляет повтор той же записи даже после закрытия первого уведомления. Текст/ссылки/заказы там не сохраняются. Системное разрешение, очистка хранилища, ОС и push-провайдер остаются внешними факторами; абсолютной гарантии «доставлено ровно один раз» Web Push не даёт.
- Отправки старше 24 часов пропускаются; тест старше 5 минут тоже. Это не даёт накопившимся после длительного выключения worker событиям внезапно появиться на телефоне. История БД сохраняется.
- Сервисные задачи получают приоритет перед массовой рекламой. Один запуск формирует до 100 получателей/событий и отправляет до 100 задач (CLI допускает до 200). Между запросами — 200 мс; абсолютный timeout HTTPS — 10 секунд. Редиректы к внешним произвольным адресам не выполняются.
- Между рекламными кампаниями минимум час, для одного покупателя — максимум одна рекламная кампания за 24 часа. Лимит резервируется при формировании получателя, даже если push не будет доставлен. Маркетинговое согласие и его версия повторно проверяются перед отправкой. Отзыв отменяет ещё ожидающие рекламные задачи; уже принятые провайдером/in-flight сообщения отозвать невозможно.
- Рекламные consent/version проверяются независимо от браузерного разрешения. Изменение рекламораспространителя меняет версию, прежнее согласие не используется. При изменении самого текста согласия также нужно повысить его версию в config/push.js.
- В сервисном тексте нет имени, телефона, состава/суммы заказа. На deep link действует обычная проверка владельца заказа. Заголовки/текст рекламной кампании вводит OWNER: в них нельзя помещать персональные данные получателей.
- «Клики» — уникальные уведомления, для которых получен авторизованный callback notificationclick. Offline/истёкшая сессия/блокировка сети могут не дать посчитать клик. Это не показатель всех открытий приложения и не показатель доставки.
- При обновлении с 11A SW ждёт закрытия всех старых вкладок/PWA. Подключение устройства проверяет capability активного worker; старый worker не будет молча зарегистрирован для push без обработчика.
- Один browser PushSubscription нельзя привязать одновременно к покупателю и OWNER. Для теста владельца использовать отдельный профиль браузера либо корректно отключить прежнюю подписку. OWNER/STAFF не получают массовую рекламу; STAFF не имеет доступа к этому разделу.

## Почему реклама выключена отдельно

В присланном архиве `privacy-policy.html` и оферта явно помечены как неутверждённые проекты без реквизитов оператора/продавца. Технический патч не подставляет выдуманные реквизиты и не утверждает документы за магазин.

Проверены доступные тексты ст. 18 38-ФЗ (предварительное согласие адресата, обязанность доказать его получение и прекращать рекламу по требованию) и ст. 9 152-ФЗ (отдельное, конкретное и подтверждаемое согласие, возможность отзыва). Реализованы отдельная форма без предустановленной галочки, идентификация через вход в аккаунт, журнал текста/версии/времени/сессии, отзыв и проверка перед отправкой. Это не заменяет заполнение и утверждение документов оператором.

Сервисные PUSH включаются через PUSH_ENABLED, рекламные — дополнительно через PUSH_MARKETING_ENABLED и реальное PUSH_MARKETING_SENDER. До массовой рассылки необходимо утвердить документы, сведения об операторе, обработке через push-провайдеров и сроках хранения. Сервисные сообщения не должны содержать рекламу под видом статусов заказа.

## Установка локально на папином ПК · CMD

Патч распаковать отдельно, например `C:\Temp\sibdel-stage11b`. Текущий проект: `C:\Users\ШУМ\WORKS\sibDel`. Остановить `npm run dev` через Ctrl+C.

```cmd
cd /d C:\Users\ШУМ\WORKS\sibDel
git remote -v
git branch --show-current
git rev-parse --short HEAD
git status --short
```

База патча — чистый `103dc89`. Перед установкой сохранить свои незакоммиченные изменения, если появились. Проверяемый способ делает резервную копию только заменяемых файлов и не трогает `.env`/uploads/БД:

```cmd
node C:\Temp\sibdel-stage11b\scripts\stage11b-patch.mjs check "C:\Users\ШУМ\WORKS\sibDel"
node C:\Temp\sibdel-stage11b\scripts\stage11b-patch.mjs apply "C:\Users\ШУМ\WORKS\sibDel" C:\Temp\sibdel-before-stage11b
node C:\Temp\sibdel-stage11b\scripts\stage11b-patch.mjs verify "C:\Users\ШУМ\WORKS\sibDel"
npm ci
npm run prisma:validate
```

Каталог backup должен быть новым, вне проекта/патча. При несовпадении хешей установщик останавливается до записи; не использовать apply поверх уже распакованного патча — тогда нужен verify. Байт-в-байт проверка может заметить CRLF/LF после checkout. Не применять Git reset/force для обхода расхождений.

Перед миграцией проверить, куда указывает локальная .env, выводя только host/port/database:

```cmd
node --input-type=module -e "import 'dotenv/config'; const u=new URL(process.env.DATABASE_URL); console.log({host:u.hostname,port:u.port||'5432',database:decodeURIComponent(u.pathname.slice(1))});"
npx prisma migrate status
```

Для локальной проверки использовать локальную dev/staging PostgreSQL, не production. Если URL указывает на рабочую БД магазина — остановиться и настроить отдельную локальную базу; пароль/полную .env в чат не отправлять. После проверки назначения БД и её backup:

```cmd
npm run prisma:deploy
npm run prisma:generate
npm run test:unit
npm run dev
```

Ожидается только одна новая миграция `20261028110000_web_push`. Если status показывает другие неожиданные pending/failed migrations, сначала выяснить причину. `prisma migrate reset`, `migrate dev` и seed для установки патча не нужны. Используется именно migrate deploy: db push не устанавливает SQL-триггеры из migration.sql.

Изначально оба PUSH-флага false. Сайт, корзина и вход продолжают работать; OWNER может готовить черновики после миграции. Для локального включения сервисных PUSH создать собственную пару VAPID:

```cmd
npm run push:keys
```

Команда генерирует ключи локально, без обращения к OpenAI или push-провайдеру. Сохранить publicKey/privateKey в действующей `.env` (не в `.env.example`), не присылать privateKey в чат и не коммитить. Пример названий переменных, значения подставить свои:

```dotenv
PUSH_ENABLED=true
VAPID_PUBLIC_KEY=<ваш publicKey>
VAPID_PRIVATE_KEY=<ваш privateKey>
VAPID_SUBJECT=mailto:<реальный контакт магазина>
PUSH_MARKETING_ENABLED=false
PUSH_MARKETING_SENDER=
```

Для разрешённых рекламных тестов после подготовки документов добавить реальное наименование рекламораспространителя и отдельно включить PUSH_MARKETING_ENABLED=true. Перезапустить Node. Новые VAPID-ключи при каждом перезапуске не генерировать: подписки браузеров связаны с исходным публичным ключом; при замене пары устройства надо переподключить.

На localhost открыть `/account/settings`, закрыть все старые окна/вкладки для активации SW 11B, снова открыть и подключить устройство кнопкой. Для проверки OWNER открыть `/admin/push` в отдельном профиле браузера, подключить своё устройство и поставить тест в очередь. Во второй CMD из проекта запустить:

```cmd
npm run push:process
```

Это реальная отправка только по уже существующей очереди вашей локальной базы, а не unit-тест. Не запускать её с production URL/ключами ради локального smoke. Если включена реклама и в очереди есть кампании, обработчик также обрабатывает их. Для первого теста оставить рекламный флаг false.

## Выкладка на Ubuntu VPS — только после отдельного подтверждения

SSH к 194.226.112.201 использовать своим настроенным пользователем. Пример каталога — `/var/www/sibdel`, PM2-процесс — sibdel. Не менять Nginx, .env, uploads и существующие systemd units копированием шаблонов.

1. Передать ZIP в отдельный staging-каталог, проверить remote/main/HEAD/status. Если сервер ещё на e4fc15c без 11A, сначала пройти установку 11A: этот патч рассчитан на 103dc89.
2. Проверить резервную копию рабочей PostgreSQL и файлов по штатному регламенту. Прочитать `prisma migrate status`: ожидается только новая миграция 11B.
3. Выполнить `stage11b-patch.mjs check` до остановки магазина. В окно обслуживания: `pm2 stop sibdel`, `apply` с новым backup-каталогом вне проекта, `verify`, `npm ci` (или runtime-only по принятому регламенту). Prisma CLI нужен для migrate/generate: выполнить их средой с dev dependencies, не оставлять сайт с новым кодом и старой схемой.
4. Выполнить только `npm run prisma:deploy`, затем `npm run prisma:generate`. При ошибке миграции остановиться; выяснить её состояние, не использовать reset/seed. Если транзакция откатилась полностью, пометка Prisma failed migrations при необходимости исправляется штатным `migrate resolve --rolled-back` только после проверки, а не автоматически.
5. Оставить PUSH_ENABLED=false при первом старте и проверить основной магазин/кабинет/админку. После настройки VAPID и контроля получателей включить сервисные PUSH; рекламный флаг оставить false до заполнения/утверждения документов.
6. Установить новый sibdel-push.service/timer с подставленными APP_USER/APP_GROUP/APP_DIR/NODE_BINARY. Проверить пользователя, рабочий каталог, права на .env и доступ к PostgreSQL/HTTPS push-сервисам. Nginx продолжает проксировать все public URL в Express; SW не должен получать долгий cache/CDN TTL.

После подготовки новых unit-файлов вручную:

```bash
sudo systemd-analyze verify /etc/systemd/system/sibdel-push.service /etc/systemd/system/sibdel-push.timer
sudo systemctl daemon-reload
sudo systemctl enable --now sibdel-push.timer
systemctl list-timers sibdel-push.timer
systemctl status sibdel-push.service
journalctl -u sibdel-push.service -n 40 --no-pager
```

Worker не запускает seed и не меняет бизнес-статусы заказов. Один service не стартует параллельно самому себе; при ручных дополнительных запусках дедупликация сохраняется, но суммарная скорость нескольких worker будет выше. Не открывать worker как публичный HTTP endpoint.

Проверки после запуска магазина:

```bash
curl -fsS https://sib-del.ru/api/health
curl -fsSI https://sib-del.ru/sw.js
curl -fsSI https://sib-del.ru/manifest.webmanifest
pm2 status
pm2 logs sibdel --lines 60 --nostream
```

Авторизованные сценарии проверять браузером. Начать с тестового устройства владельца и одной тестовой учётной записи. Не вставлять session cookies, endpoints, privateKey и полную .env в журнал/чат. До фактического подтверждения работы таймера нельзя считать кнопку «Отправить» доставившей сообщения — она ставит работу в очередь.

## Откат без отката БД

1. Остановить/отключить новый timer и активный worker, затем остановить PM2. Уже принятые push-провайдером сообщения могут ещё прийти в пределах TTL.
2. Сохранить каталог новой миграции для истории Prisma. Восстановить код через installer backup; installer не перезапишет последующие пользовательские изменения и поддерживает частичное применение.
3. Вернуть в проект папку `prisma/migrations/20261028110000_web_push` из сохранённого патча, если кодовый rollback её убрал: запись применённой миграции остаётся в БД, её файл должен быть доступен. Схему БД не удалять, SQL DOWN не выполнять. Новые таблицы и триггеры безопасно остаются: старый 11A их не использует, триггеры продолжают сохранять будущие события без отправки.
4. Восстановленные файлы generated/prisma соответствуют старому коду 11A; после npm ci запустить PM2. Старый SW 11A возвращается по тому же /sw.js. Закрыть все окна/PWA, открыть снова и проверить обновление/активацию старой версии; принудительно перезагружать checkout нельзя. Retirement worker нужен только если откатывается всё PWA целиком, для отката 11B→11A он не нужен.

```bash
sudo systemctl disable --now sibdel-push.timer
sudo systemctl stop sibdel-push.service
pm2 stop sibdel
node /tmp/sibdel-stage11b/scripts/stage11b-patch.mjs rollback /var/backups/sibdel-code/stage11b-before
mkdir -p /var/www/sibdel/prisma/migrations/20261028110000_web_push
cp /tmp/sibdel-stage11b/prisma/migrations/20261028110000_web_push/migration.sql /var/www/sibdel/prisma/migrations/20261028110000_web_push/migration.sql
cd /var/www/sibdel
npm ci
pm2 restart sibdel
curl -fsS https://sib-del.ru/api/health
```

На Windows — тот же `rollback` с путём локального backup; вернуть файл миграции аналогично. Не запускать генерацию клиента 11B после возврата к исходному schema 11A и не создавать «исправляющую» destructive migration. VAPID private key и существующую .env не перезаписывать при откате.
